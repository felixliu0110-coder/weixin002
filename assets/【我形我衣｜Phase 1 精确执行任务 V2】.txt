==================================================
六、最重要：视频验证必须发生在 CACHE 查询之前
==================================================

当前 aiTryon 的实际顺序大致是：

解析人物
→
解析衣物
→
生成 cacheKey
→
查询 cache
→
consumeQuota
→
imageTaskId 验证

这个顺序必须修改。

mode === "video" 时：

必须先完成 imageTaskId 的完整验证。

然后才能查询视频 cache。

最终顺序必须是：

requireLogin
↓
avatarViewId requireId
↓
garmentIds requireArray + requireId
↓
avatar ownership
↓
resolveGarments
↓
如果 mode === video：
    imageTaskId requireId
    ↓
    getOwnedDoc(tryon_tasks, imageTaskId, openid)
    ↓
    imgTask.type === "ai_image"
    ↓
    imgTask.status === "success"
    ↓
    imgTask.tryon_image_url 非空
    ↓
    imgTask.avatar_view_id === 当前 avId
    ↓
    normalized(imgTask.garment_ids) === normalized(gIds)
↓
计算 cacheKey
↓
查询 pending / cache
↓
如果 cache/pending 命中：
    直接复用
    不扣额度
↓
consumeQuota
↓
创建视频任务
↓
Provider

特别要求：

【imageTaskId 验证不得出现在 cache 查询之后】

【imageTaskId 验证不得出现在 consumeQuota 之后】

==================================================
七、视频任务一致性
==================================================

必须保证：

当前视频请求：

avatarViewId = A
garmentIds = [X, Y]

imageTaskId 对应图片任务必须同时满足：

imgTask.user_id = 当前用户

imgTask.type = "ai_image"

imgTask.status = "success"

imgTask.tryon_image_url 非空

imgTask.avatar_view_id === A

imgTask.garment_ids 与 [X, Y] 为同一集合

集合比较规则：

function normalizeGarmentIds(ids) {
  return (ids || []).slice().sort().join(",");
}

然后：

normalizeGarmentIds(imgTask.garment_ids)
===
normalizeGarmentIds(gIds)

禁止修改数据库中的数组。

禁止修改当前 cache 的排序规则。

==================================================
八、为什么必须这样
==================================================

必须防止：

用户当前请求：
Avatar A + Garment X

但是 imageTaskId：
Avatar B + Garment Y

即使：
B/Y 图片任务属于当前用户
且 status=success
且 tryon_image_url 存在

也必须拒绝。

同时必须防止：

错误 imageTaskId
+
当前组合恰好存在视频 cache
=
错误地返回 success

所以：

【视频 imageTaskId 验证必须先于 cache hit】
