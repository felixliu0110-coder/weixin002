==================================================
一、项目现实约束
==================================================

本项目是：

【微信小程序】

不是 AI 平台。
不是 SaaS 平台。
不是 AI 基础设施平台。
不是模型训练项目。

核心产品目标：

用户上传/选择人物
+
选择衣物
↓
生成“用户穿着该衣物”的真实感效果图。

项目必须：

1. 能真正上线；
2. 成本可控；
3. 架构简单；
4. 后期可以维护；
5. 不依赖大量第三方收费服务；
6. AI 模型可以更换；
7. 不因为换模型而重写业务系统。

==================================================
二、最高成本约束
==================================================

整个项目允许：

【最多一家外部付费 AI 厂商】

可以是：

- OpenAI
- Seedance
- 其他最终经过测试选定的模型厂商

目前不得提前确定是哪一家。

最终模型由开发者通过实际 POC 测试决定。

除此之外：

禁止为了单独功能增加其他付费 AI API。

禁止：

- 单独购买人体识别 API
- 单独购买人脸识别 API
- 单独购买抠图 API
- 单独购买衣物识别 API
- 单独购买 VTON API
- 单独购买 OCR API
- 单独购买视频 API
- 单独购买图片增强 API
- 单独购买质量检测 API
- 多家 AI API 同时付费

==================================================
三、服务器成本原则
==================================================

允许使用云服务器。

但：

【只有在微信云开发/云函数无法合理承担某项任务时才增加服务器。】

默认优先：

微信小程序
+
微信云开发/云函数
+
云存储
+
唯一付费 AI

如果以后发现：

- 长任务
- 队列
- Worker
- 大文件处理
- Provider 回调
- 特殊运行环境

确实不适合云函数，

才增加：

【一台必要的普通云服务器】

禁止为了本地 AI 模型专门租 GPU 服务器。

==================================================
四、本地开源模型不是当前必选项
==================================================

本项目当前：

【不部署本地开源 AI 模型。】

架构可以预留：

LocalModelProvider

但不实际部署。

只有未来同时满足：

1. 有成熟开源模型；
2. 商业许可证允许；
3. 不需要额外购买 GPU；
4. 现有服务器可以承担；
5. 实际效果达到产品要求；
6. 能明显降低长期成本；

才考虑部署。

不能因为“开源模型听起来便宜”就提前部署。

==================================================
五、禁止过度架构
==================================================

不要建立：

- Kubernetes
- GPU 集群
- 微服务集群
- MQ 集群
- 独立 AI Gateway
- 独立模型管理平台
- 独立图片处理平台
- 独立视频平台

V1 不需要这些。

采用：

【模块化单体 + 微信云函数/必要时单服务器】

==================================================
六、AI 的真正职责
==================================================

AI 只负责：

【生成式视觉任务】

即：

人物 + 衣物
↓
生成穿搭效果图

如果最终模型同时支持：

图生视频

则可以由同一家 Provider 承担视频。

AI 不应该负责：

- 数据库
- 权限
- 额度
- 缓存
- 用户身份
- 文件生命周期
- 任务状态
- 业务规则
- 计费逻辑。

==================================================
七、所有能用程序解决的问题，不交给 AI
==================================================

例如：

图片：

- 格式检查
- 文件大小检查
- 尺寸检查
- EXIF 方向
- 缩放
- 裁剪
- 压缩
- Hash
- 去重
- 临时文件清理

全部使用：

程序/图像处理库。

不要增加 AI 调用。

==================================================
九、三视图重新定位
==================================================

当前：

createAvatarViews

保留。

但重新定义为：

【可选人物展示能力】

不是：

【V1 试穿必要能力】

新的静态试穿：

人物真实照片
↓
人物资产
↓
AI 试穿

不要求：

↓

↓

1. 多一次 AI 成本；
2. 增加等待时间；
3. AI 可能改变人物；

5. 没有证据证明三视图一定提高最终试穿质量。

==================================================

当前：

ensureGarmentViews

如果以后测试证明：

再考虑启用。

不是现在默认启用。

==================================================
十二、用户主动选择衣物类别
==================================================

V1 不需要强制增加自动衣物识别 AI。

用户选择：

- 上衣
- 裤子
- 连衣裙
- 外套
- 鞋
- 帽子
- 其他

服务端做基本合法性校验。

用户主动选择本身可以减少 AI 判断成本。

==================================================
十三、V1 穿搭组合限制
==================================================

数据库可以支持多件衣物。

但：

【数据库支持多少 ≠ AI 必须一次生成多少。】

V1 控制复杂度。

优先：

A：

一件上衣

B：

上衣 + 下装

C：

一件连衣裙/连体衣

暂不默认：

10 件衣物同时生成。

原因：

衣物越多：

- 提示词复杂度越高
- 参考图越多
- 模型稳定性越低
- 成本越高
- 失败率越高。

==================================================
十四、核心 AI 调用
==================================================

核心目标：

【尽可能一次 AI 调用完成一次静态试穿。】

不要设计成：

AI 人物分析
+
AI 三视图
+
AI 衣物分析
+
AI 四视图
+
AI 试穿
+
AI 质量检查

这样的多次调用链。

正确：

人物真实图片
+
衣物真实图片
+
用户选择
↓
一次核心生成
↓
试穿结果

不能修改：

权限。

cloudfunctions/aiTryon/index.js

已经承担大量职责：

- 缓存
- 额度
- 图片生成
- 视频生成

避免一次大重构导致现有项目无法运行。

==================================================

==================================================

项目当前存在：

身材参数
肤色
腿长
三围等。

这些数据：

【可以作为生成提示/约束的辅助信息】

==================================================

生成策略优先级：

多个参考图辅助。

不默认重新生成一个全新人物。

==================================================

衣物真实图片作为主要参考。

尽量保持：

图案

版型
长度
领口

不要先让 AI 重绘服装再拿重绘结果试穿。

==================================================

禁止无必要地：

原图
↓
AI 三视图
↓
AI 四视图

==================================================

当前项目已经有试穿缓存。

user
+
person asset version
+

+
outfit version
+
provider
+
model
+

+
generation config

这样：

模型变化：

缓存隔离。

衣物变化：

缓存隔离。

生成逻辑变化：

缓存隔离。

==================================================
二十六、缓存命中不消耗 AI
==================================================

如果相同：

人物
+
衣物
+
组合
+
模型
+
参数

已经生成成功：

直接返回缓存。

不要重新调用 AI。

==================================================
二十七、重新生成
==================================================

用户点击：

【重新生成】

才产生新的生成请求。

不能因为页面刷新就重新生成。

不能因为重复点击就重复扣额度。

==================================================
二十八、任务幂等
==================================================

每个请求：

request_id

相同请求：

只能产生一个任务。

如果已经：

queued
processing

直接返回现有任务。

不能重复调用 AI。

==================================================
二十九、额度
==================================================

用户层面的规则：

【一次用户主动发起的试穿 = 一次额度】

而不是：

【AI API 调用一次 = 一次额度】

内部如果：

缓存命中
→ 不扣

重复提交
→ 不重复扣

预处理失败
→ 不扣

Provider 参数错误
→ 回补

Provider 临时失败
→ 回补

系统异常
→ 回补

==================================================
三十、视频
==================================================

V1：

【静态试穿优先。】

视频不自动生成。

流程：

静态试穿成功
↓
结果页
↓
用户主动点击“生成视频”
↓

==================================================
三十一、视频不能影响静态试穿
==================================================

不能把静态任务改成失败。

应该：

视频单独失败。

用户可以重新生成视频。

==================================================
三十二、视频成本控制
==================================================

视频属于高成本能力。

必须：

用户主动触发。

不能：

上传人物自动生成视频。

不能：

试穿完成自动生成视频。

不能：

后台偷偷生成。

==================================================
三十三、结果质量检查
==================================================

V1 不增加付费 AI 质量检测。

- 文件是否存在

- 尺寸是否正常
- 文件是否损坏
- 是否成功存储

再使用：

简单规则检查。

例如：

明显黑屏
明显白屏
尺寸异常

直接失败。

三十四、不要设计伪 AI 评分
==================================================

没有真实训练数据：
