## 1. 产品概述

### 1.1 产品定位

「我形我衣」是一款生活服务类微信小程序，核心能力是**基于 AI 写实人物三视图的虚拟试穿**：

1. 用户通过微信身份进入小程序，填写身高、体重、三围等身材参数，并可选上传人脸照片与全身照，由 AI 生成写实人物三视图（正面图/侧面图/背面图），生成一次并复用；
2. 用户从系统模板衣物库选择衣物或上传自己的衣物照片（手动填写名称与分类），服务端校验衣物归属后以原图作为参考，结合人物三视图生成照片级试穿效果图；
3. 试穿结果以效果图呈现，用户确认满意后可**主动选择**生成 180° 原地转身视频（图片生成与视频生成是两个独立阶段，视频不是每次试穿必须执行）；
4. 试穿结果支持收藏、保存到相册、保存模板、分享。

### 1.2 解决的问题

- 网购衣物无法看到真实上身效果，买错尺码、款式压箱底；
- 想按自己的真实身材（而非模特身材）预览穿着效果；
- 衣柜衣物多但缺乏搭配思路（搭配建议在 V2 提供）。

### 1.3 产品目标（V1）

- 北极星指标：**人均每周有效试穿次数**（成功生成并保存 ≥1 次试穿效果图）；
- 关键结果：人物形象创建完成率 ≥60%；首次试穿转化率 ≥40%；试穿生成成功率 ≥85%；生成耗时以供应商实际能力为准（前端全程展示进度）。

> 注：V1 前期为**自用 / 小范围体验阶段**，以上指标用于自我校验产品质量，暂不作为商业化考核标准。

### 1.4 目标用户

- 核心人群：18–35 岁，习惯网购服饰、在意穿搭效果的男女用户；
- 次要人群：服装店主、穿搭达人（用生成结果做展示或选品）。

### 1.5 设计原则

1. **隐私优先**：照片与身体数据最小化收集、加密存储、可一键删除；
2. **真实优先**：试穿结果追求照片级真实感，与"AI 生成效果"的说明并存；
3. **简单优先**：首次创建人物形象 5 分钟内可完成，支持分步保存；
4. **合规先行**：AI 生成标识、深度合成备案、内容安全审核贯穿全流程。

## 3. 功能需求

### 3.1 用户身份与首次引导

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| FR-01 | 微信 openid 身份体系 | 用户通过微信进入小程序，服务端通过 `cloud.getWXContext().openid` 获取 openid 作为用户唯一身份标识；不依赖手机号登录 |
| FR-02 | 首次创建引导 | 首次进入展示创建人物形象引导流程，分步填写、每步可保存 |
| FR-03 | 隐私授权 | 弹窗明示人脸照片与身体数据的用途、存储方式、删除方式；未授权前不采集任何照片 |

### 3.2 人物形象创建与编辑

> **人物形象**（产品侧称谓）是用户用于 AI 试穿的人物资产，由人物基础参数 + 人物三视图组成。后端技术对象沿用 `avatar_profile` / `avatar_views` 命名。

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| FR-04 | 身材参数录入 | 必填：身高、体重、性别；选填：腰围、胸围、臀围、腿长、颈长、肩宽、臂长、鞋码、肤色 |
| FR-05 | 缺省估算 | 仅填身高体重时，按性别给出默认体型特征，用户可逐项修改 |
| FR-06 | 人脸照片上传（选填） | 正面照 1 张（jpg/png）；上传则用于提升人物三视图的面部/发型一致性，不要求 100% 相似；不上传时使用性别化默认形象 |
| FR-06a | 性别特征呈现 | 无论是否上传人脸照片，人物形象均按所选性别呈现体型特征，保证男女形象可区分 |
| FR-07 | 全身照上传（选填） | 用于肤色、体态校准；可跳过 |
| FR-08 | 生成人物三视图 | 创建向导完成时，服务端根据身材参数与照片（如有）调用 AI 生成写实人物三视图（正面图/侧面图/背面图），**生成一次并复用**；生成中显示进度，进度到 100% 才算完成 |
| FR-09 | 查看人物三视图 | 人物形象页展示 AI 生成的三视图（正面图/侧面图/背面图），直观预览自己的身材比例；**不是传统 3D 渲染** |
| FR-10 | 编辑人物形象 | 身材参数可修改并重新生成三视图；**完整的历史版本保存与恢复能力暂未形成当前 V1 的完整闭环**，修改后生成新版本覆盖旧版本 |
| FR-11 | 删除人物形象 | 一键删除人物形象及关联的照片与生成数据（异步清理，7 天内完成） |

### 3.3 衣物试穿（核心功能）

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| FR-12 | 试穿入口 | 人物形象页"去试穿"按钮、首页快捷入口、试衣页五分类衣物库 |
| FR-13 | 模板衣物库 | 试衣页按五个分类组织：上衣 / 裤子 / 头饰 / 鞋子 / 其他；内置系统模板衣物展示在各分类下；分类卡片显示该分类衣物件数 |
| FR-14 | 上传衣物图片 | 支持相册/拍照，jpg/png；用户**手动填写**衣物名称并选择分类（上衣/裤子/头饰/鞋子/其他），**不做自动品类识别**；上传原图保存至云存储，试衣页保存的一律为用户原图 |
| FR-15 | 原图直用（不做抠图） | 上传仅做格式/大小校验与内容安全检测；**不做抠图、背景移除、透视归一化或透明化处理**，原图直接作为 AI 生成参考图；非衣物、多人、涉敏图片给出明确提示并拦截 |
| FR-16 | 服装参考增强能力（实验性） | 服装四视图能力（`ensureGarmentViews` / `garment_views`）保留在系统中，作为后续实验性增强能力。**当前默认 Try-On 主流程不再强制执行服装四视图生成。** 当前默认图片 Try-On 使用：人物三视图 composite + 服务端解析并校验后的衣物原图（`garments.original_file_id`）作为 AI 生成输入。`ensureGarmentViews` 与 `garment_views` 仍保留，但不属于当前默认 Try-On 前置步骤。是否重新接入服装四视图，必须经过独立 POC 验证后再决定（相同 Provider、相同测试样本、可重复的 A/B 对比）。禁止写任何未经实测的效果提升结论。删除原图时对应四视图记录与文件一并删除 |
| FR-17 | AI 试穿图片生成 | 提交后进入异步生成队列，展示"生成中"状态与预计时长；**以人物三视图 composite 作为人体基准，以服务端解析并校验后的衣物 `originalFileId` 对应原图作为服装参考，调用当前生产 AI Provider 生成试穿效果图**；完成后通过微信订阅消息通知；同衣物组合 7 天内缓存复用（秒回），生成失败自动重试 1 次 |
| FR-17a | 试穿一致性 | 生成时以 AI 人物三视图作为人体底图，人脸照片（如已上传）用于面部相似度，确保试穿效果图中身材比例来自用户档案；衣物版型、颜色、细节与参考图一致 |
| FR-17b | **图片与视频分离：用户主动生成视频** | 试穿图片生成后，用户在结果页**主动选择**"生成动态视频"入口，进入独立视频生成页；视频以试穿效果图 + 人物三视图为参考，调用 AI 生成 **180° 原地转身视频**；视频为可选步骤，非每次试穿必须执行；服务端根据 `imageTaskId` 查询图片任务并做归属校验，不信任客户端直接传入的效果图 URL |
| FR-18 | 结果管理 | 试穿记录按时间倒序；试穿结果以效果图形式预览（如有视频则附带视频），支持收藏、保存到相册、分享 |
| FR-19 | 分享规范 | 分享卡片必须标注"AI 生成效果，仅供参考"；结果带「AI 生成」标识 |
| FR-20 | 收藏 | 试穿结果可收藏（独立收藏页）；收藏后可选择是否同时保存到相册 |
| FR-20a | 对比视图 | 同一人物形象不同衣物并排对比；他人人物形象不可见、不可共享 |
| FR-21 | 失败处理 | 生成失败自动重试 1 次；仍失败则提示原因（如图片质量不足），不重复计费/不重复消耗额度 |

#### 实验状态说明

当前生产路径已验证的事实：

1. 人物三视图已作为现有人物资产使用。
2. 图片 Try-On 当前直接使用人物 composite + 衣物原图。
3. 服装四视图能力已保留，但当前不作为默认前置步骤。
4. 是否使用服装四视图能够改善最终试穿质量，当前尚无本项目真实 A/B POC 结论。
5. 后续必须通过相同 Provider、相同测试样本、可重复的 A/B POC 验证后再决定是否重新接入。

## 5. 业务流程

### 5.1 首次创建人物形象

登录（微信 openid）→ 隐私授权 → 基本信息（性别/身高/体重）→ 身材参数（选填补充，缺省估算可改）→ 人脸照片上传（选填）→ 全身照（选填）→ AI 生成人物三视图（正面图/侧面图/背面图，生成一次并复用）→ 预览确认 → 创建完成。

异常分支：
- 照片不合格 → 提示重拍（正脸、光线均匀）；
- 参数缺失 → 使用估算值，标注"估算"，允许后续修改；
- 中途退出 → 已填步骤自动保存，下次继续。

### 5.2 上传衣物试穿（图片生成）

选择/上传衣物图 → 填写名称与分类（上衣/裤子/头饰/鞋子/其他，手动选择）→ 内容安全检测 → 服务端解析衣物归属 → 结合人物三视图 composite + 衣物原图生成试穿效果图 → 订阅消息通知 → 查看/收藏/保存/分享。

### 5.3 生成动态视频（用户主动选择）

试穿效果图生成成功后 → 用户在结果页主动点击"生成动态视频" → 进入视频生成页 → 服务端根据 `imageTaskId` 查询图片任务 → 校验 ownership → 获取试穿效果图 URL → AI 图生视频（180° 原地转身）→ 轮询进度 → 展示视频。

**关键**：视频生成是独立阶段，必须基于已成功的图片任务，不信任客户端直接传入的效果图 URL。

### 5.4 异常分支

- 生成失败 → 自动重试 1 次 → 仍失败则提示原因（不重复消耗额度）；
- 内容违规 → 拦截并提示，不进入生成流程；
- 额度不足 → 拒绝创建任务，提示"今日免费额度已用完"。

## 9. 技术架构（概述）

### 9.1 客户端

- 原生微信小程序（pages 原生页面 + 自定义组件 + 自定义 TabBar）；
- AI 能力全部走云函数统一接口，前端不直接接触供应商 API Key；
- 云函数：`aiTryon`（图片/视频生成、收藏、历史、额度）、`createAvatarViews`（人物三视图生成）、`ensureGarmentViews`（服装四视图生成）、`uploadGarment`（上传衣物+内容安全检测）、`auth`（身份）、`cleanup`（定时清理）。

### 9.2 服务端

- 微信云开发：云函数（AI 生成编排、内容安全检测、身份校验、存储管理）+ 云数据库 + 云存储；
- 生成任务采用异步流程：提交 → 排队 → 调用 AI 服务 → 写库 → 推送订阅消息；
- AI 生成图片/视频自动保存至云存储（cloud:// 文件 ID）；

### 9.3 AI 服务（统一接口层，可替换供应商）

| 能力 | 说明 | 选型标准 |
| --- | --- | --- |
| 人物三视图 | 创建向导完成时生成写实三视图（正面图/侧面图/背面图，composite 合成图），一次生成后复用 | 人像真实感、备案资质、单价 |
| 服装四视图（实验性增强能力） | 以用户原图为参考生成 2×2 四视图（正面/45° 斜侧/局部细节/背面），首次生成并缓存；**当前不属于默认 Try-On 前置步骤，是否重新接入须经 POC 验证** | 版型/颜色/细节一致性 |
| 试穿效果图 | **人物三视图 composite + 服务端解析并校验后的衣物原图/参考图** → 照片级试穿效果图；客户端传入的 garmentId 需经服务端解析+ownership 校验后才作为生成依据 | 生成速度、人衣一致性、SLA |
| 试穿视频 | **基于已成功的图片任务**（服务端根据 imageTaskId 查询+校验 ownership）+ 人物三视图 + 视频提示词 → **180° 原地转身**动态视频（用户主动选择生成） | 生成速度、动作自然度、一致性、SLA |
| 内容审核 | 微信内容安全 API（imgSecCheck），上传衣物时检测 | 覆盖范围、响应速度 |

> 当前接入 Agnes AI（生图 + 生视频），通过可插拔 AIGC 适配器支持后续更换模型/供应商。

### 9.4 安全能力（V1 已实现）

| 能力 | 说明 |
| --- | --- |
| 用户身份校验 | 服务端统一从 `cloud.getWXContext().openid` 获取身份，不信任客户端传入的 openid/user_id |
| Ownership 校验 | 所有资源操作（查询/写入/删除）均校验 user_id 归属；旧数据缺归属视为不可访问 |
| SSRF 防护 | 图片下载仅允许公网 HTTPS URL；拒绝 localhost/内网/回环/私网 IP；DNS 解析后校验 IP；重定向最多 3 次且每次重新校验 |
| AI Key 安全 | API Key 存储在云函数环境变量，前端不可见 |
| 回调鉴权 | 异步任务回调走服务端校验，不信任回调携带的任意 URL 作为授权依据 |
| 输入校验 | 所有客户端输入（ID/字符串/数组/枚举）均在服务端校验 |
| 额度原子扣减 | 事务防并发超扣；失败回补策略由调用方决定 |
| 任务状态机 | queued → processing → success/failed；拒绝非法状态跳转 |
| 删除资源清理 | 账户删除时清理所有集合数据 + 云存储文件；幂等，同用户存在未完成作业时复用 |
