## 争议 1：为什么所有用户都必须先 AI 生成人物锚定图？

### ChatGPT 的立场

用户上传合格照片 → 直接用，不该强制 AI 重建。AI 重建引入漂移，结果是"像用户的人"而非"用户本人"。

### 我的回答：**你对了，我错了。**

VTON 的核心任务就是"给真实的人换衣服"。真实照片是 VTON 能拿到的最好人物输入。AI 重建是一个有损变换，必然降低身份保真度。

我逐条推翻自己原来的理由：

| 我原来的理由 | 为什么是错的 |
|------------|------------|
| 白底更标准，VTON 更稳定 | VTON 模型内置人体分割，不需要白底输入。VITON-HD、DressCode 评测集都含非白底图片，模型表现没有显著下降 |
| 固定姿态更利于 VTON | VTON 的 warping 模块专门处理姿态差异。正面前排只是最简单情况，不是唯一可接受情况 |
| AI 图参数可控，体型更准 | AI 图的体型由模型对 prompt 的理解决定，偏差不可预测。真实照片的体型就是用户的真实体型，零偏差 |
| 同一张锚定图保证后续结果一致 | 用同一张真实照片做 VTON 同样一致。一致性来自"输入不变"，不来自"输入是 AI 生成的" |

### 修正方案

```
用户上传照片
    ↓ 照片质量自动检测（前端 MediaPipe）
    ↓
├── 合格 → 直接作为 VTON 人物输入（0 次 AI 调用）
│   检测标准：
│   - 单人（人物检测恰好 1 人）
│   - 正面（人脸偏航角 < 30°）
│   - 全身（头到脚均在画面内）
│   - 清晰（拉普拉斯方差 > 阈值，非模糊）
│   - 身体无遮挡（肩/腰/膝关键点可见率 > 80%）
│   - 分辨率（短边 ≥ 512px）
│
├── 不通过 + 可修复问题
│   → 给用户具体反馈："请站在纯色墙前重新拍摄"
│   → 用户重新上传 → 再次检测
│
└── 不通过 + 用户无照片可用
    → AI 从参数生成锚定图（降级方案）
    → 明确标注"AI 估算形象，效果可能不如真实照片"
    → 这是唯一需要 AI 人物生成的场景
```

**判定：ChatGPT 胜。方案修正为"质量合格直接用原图，不合格才 AI 重建"。**

## 争议 2：VTON 到底能不能直接支持 1～10 件衣物？

### ChatGPT 的立场

VTON 基本输入是 person image + garment image，即单衣物。不能因为"能单衣换装"就推导"能自然处理 10 件"。

### 我的回答：**你对了。当前没有任何 VTON 模型支持 10 件衣物。**

逐条回答你的 10 个问题：

**1. 推荐的具体 VTON 模型？**

V1 不锁定具体模型（见争议 6），但候选方向是 API 化的 VTON 服务。原因：微信云开发没有 GPU，无法自部署。

**2. 它实际支持几件衣物？**

1 件。标准 VTON 输入 = 1 张人物图 + 1 张服装图。

**3. 多件衣物是什么方式？**

多次 VTON 串联。但有严格限制：
- 上装 + 下装：可行。两个区域不重叠，各自独立替换，无误差累积
- 上装 + 上装（内搭 + 外套）：不可行。标准 VTON 替换整个上半身区域，无法做到"在 T 恤外面套外套"
- 3 件以上：不可行。误差累积不可控

**4. 多层衣物如何保证遮挡关系？**

无法保证。标准 VTON 没有遮挡关系概念——它替换整个目标区域的服装。解决遮挡关系需要 multi-garment VTON 或 inpainting 分区，目前都不成熟。

**5. 两件上装如何处理？**

V1：不支持。2 件上装 = VTON 替换整个上半身两次，第二次会覆盖第一次的结果。

**6. 两条裤子如何处理？**

V1：不支持。逻辑上不可能同时穿两条外裤。

**7. 外套和内层衣物如何处理？**

V1：不支持叠穿。只能选 1 件上装试穿。V1.5 尝试 inpainting 策略（VTON 穿内搭 → inpainting 画外套区域），但质量不可预测。

**8. 鞋子是否属于 VTON 范畴？**

部分模型支持（DressCode 含 shoes 类别），但鞋子 VTON 质量通常比上装/下装差（脚部区域小、变形多）。V1 不建议支持。

**9. 配饰是否支持？**

不支持。配饰试穿需要专门的 accessories try-on 模型，与服装 VTON 是不同技术路线。

**10. 最多 10 件是否只是产品层面的选择数量？**

是的。10 件是产品层的"收藏/搭配"功能。实际 VTON 生成时：

```
V1 试穿能力：
  模式 A：1 件上装（1 次 VTON 调用）
  模式 B：1 件下装（1 次 VTON 调用）
  模式 C：1 件上装 + 1 件下装（2 次 VTON 调用，分区替换）

V1 不支持：
  - 2 件上装叠穿
  - 2 件下装
  - 鞋子
  - 配饰
  - 3 件及以上

前端限制：
  - 试穿选择页最多勾选 2 件
  - 必须满足"0-1 上装 + 0-1 下装"的组合规则
  - 选 2 件上装时提示"暂不支持叠穿，请选择 1 件试穿"

产品层面的"10 件搭配"：
  - 保留为穿搭收藏/灵感板功能
  - 用户选 10 件是"我想要的搭配方案"
  - 实际试穿只能选其中 1-2 件生成效果图
```

**判定：ChatGPT 胜。V1 严格限制 1-2 件（0-1 上装 + 0-1 下装）。10 件只是收藏功能，不是 VTON 输入数量。**

## 争议 3：体型偏差阈值为什么是 15%？

### ChatGPT 的立场

15% 没有任何数据支撑（无真实用户数据集、无误差分布、无 ROC 曲线、无阈值实验），不应作为产品硬规则。

### 我的回答：**你对了。15% 无依据，必须删除。**

我没有任何数据能证明 15% 是合理阈值。这不是"数字需要微调"的问题——是整个"自动体型判定"的框架都没有经过验证。

更深层的质疑是对的：不只是 15% 没依据，从 2D 图片做体型自动判定本身就有未经验证的假设——MediaPipe 关键点精度够不够？穿衣服的人的肩宽/腰宽像素值可靠吗？同一体型穿宽松衣服和穿紧身衣服的关键点比例完全不同，BMI 类别能从图像比例中可靠判断吗？

**没有数据支撑的自动判定系统比没有判定系统更危险**——它给出"看起来科学"的错误判断，误导决策。

### 修正方案

```
V1 体型策略：纯数据收集，不做自动判定

1. 生成锚定图后（仅降级场景），记录以下数据：
   - 用户输入参数（身高/体重/BMI/三围）
   - 生成图的 MediaPipe 关键点坐标
   - 关键点比例（肩宽/身高、腰宽/身高等）

2. 数据仅记录，不做自动判定
   - 不拦截任何生成结果
   - 不向用户显示体型偏差提示
   - 仅作为后台日志

3. 积累 100+ 条数据后：
   - 人工抽样标注：这条结果体型是否合理？
   - 计算各比例指标与人工标注的相关性
   - 确定哪些指标有判别力、哪些没有
   - 基于数据拟合阈值（ROC 曲线选最优工作点）

4. 有数据支撑后再上线自动判定（V2）
```

**判定：ChatGPT 胜。15% 阈值删除。V1 不做自动体型判定，改为纯数据收集。**

## 争议 4：BMI 到底能不能作为人体体型约束？

### ChatGPT 的立场

BMI 只能用于粗粒度异常检测，不能作为主要人体几何约束。相同 BMI 的肌肉型和脂肪型体型完全不同。用户提供的真实测量值应优先于 BMI。BMI 最多"辅助判断体重是否异常"，不能"推导身体具体几何形态"。

### 我的回答：**核心观点同意，但有一个必须澄清的边界。**

### 我同意的部分

**BMI 不能作为主要人体几何约束——100% 正确。**

一个 BMI 26 的人可能是：
- 健身者：宽肩、窄腰、肌肉线条明显
- 久坐者：窄肩、粗腰、脂肪分布均匀

这两个人的肩宽、胸围、腰围、臀围、腿长完全不同。如果系统只用 BMI 来推导体型，就会把这两种人画成同一种身材——这是错的。

**真实测量值应优先——100% 正确。**

如果用户提供了肩宽、胸围、腰围、臀围，这些数据直接决定了视觉上的身型分类（hourglass / inverted triangle / pear / rectangular），比 BMI 精确得多。我的参数翻译引擎已经处理这种情况：

```
肩≈臀>腰 → hourglass silhouette
肩>臀 → inverted triangle, broader shoulders
臀>肩 → pear shape, wider hips
肩≈腰≈臀 → rectangular, minimal waist definition
```

这些判断完全不需要 BMI 参与。

### 我要澄清的边界

**BMI 在一个特定场景下仍然有用：当用户只提供了身高和体重时。**

实际情况是：大部分用户不会填满 9 项身体参数。他们会填身高 + 体重（因为这两个最容易获取），可能再填 1-2 个围度。在这种情况下：

| 用户提供了 | 身型判断的精度 | BMI 的角色 |
|-----------|--------------|-----------|
| 身高+体重+肩宽+胸围+腰围+臀围+腿长 | 高精度（直接判断 hourglass/pear 等） | 无需 BMI，已有更好数据 |
| 身高+体重+腰围 | 中精度（能判断胖瘦趋势+腰线） | BMI 辅助判断整体胖瘦，腰围辅助判断身型 |
| 身高+体重 | 低精度（只能判断整体胖瘦） | **BMI 是唯一可用的身型信号** |
| 什么都没有 | 无精度 | 不适用（用真实照片，无需参数） |

当用户只提供身高+体重时，BMI 不是在"推导身体几何形态"——没有人会用 BMI 推算"腰围是 78cm"。BMI 的作用是**选择一个粗粒度的 prompt 描述词**：

```
BMI < 18.5 → "slender, visibly thin, narrow frame"
BMI 18.5-24 → "average build, naturally proportioned"
BMI 24-28 → "solid build, broader frame"
BMI > 28 → "full-figured, substantial build"
```

这是 prompt 层面的粗分类，不是工程层面的精确约束。把 "solid build" 写进 prompt，模型画出来就是一个偏壮的人；把 "slender" 写进去，画出来就是偏瘦的人。这不是"根据 BMI 推导几何形态"，而是"用 BMI 选择一个视觉描述方向"。

### 最终立场

```
体型约束优先级（从高到低）：

1. 真实照片（最高优先级）
   → 用户上传的合格照片直接作为 VTON 输入
   → 照片本身就是最真实的体型约束
   → 不需要任何参数推导

2. 完整测量值（肩宽/胸围/腰围/臀围/腿长）
   → 用于参数翻译引擎，生成精确的身型描述
   → hourglass / pear / inverted triangle / rectangular
   → 比任何 BMI 分类都精确

3. 部分测量值（身高+体重+1-2围度）
   → 用可用的围度做身型判断
   → BMI 辅助判断整体胖瘦趋势

4. 仅身高+体重
   → BMI 是唯一可用的身型信号
   → 只能做粗粒度胖瘦分类（4 档）
   → 无法判断 hourglass/pear 等具体身型
   → 这是最低可接受的精度，但好过"完全没有身型信息"

5. 完全没有参数
   → 仅在降级场景（AI 锚定图）中才需要参数
   → 如果用户有合格照片，这一层根本不触发
```

**判定：ChatGPT 胜。BMI 不能作为主要人体几何约束，真实测量值优先。但 BMI 在"用户只提供身高体重"的场景下是最低可用身型信号，用于 prompt 粗分类而非精确推导。**

## 争议 5：OpenPose 是否等于精确体型控制？

### ChatGPT 的立场

OpenPose 提供关键点 + 骨骼位置 + 姿态信息，不能直接告诉模型"腰围 78cm"。身高/胸围/腰围/臀围和 OpenPose 是两个不同维度。如果方案中存在"OpenPose 可以直接解决体型精度"这种表述，需要修改。

### 我的回答：**你对了。OpenPose 不是体型模型。**

### OpenPose 到底能做什么

| 能力 | 说明 | 可靠程度 |
|------|------|---------|
| 人体关键点检测 | 标出肩/肘/腕/髋/膝/踝等 2D 位置 | ✅ 核心能力，可靠 |
| 姿态估计 | 判断站立/坐/侧身等姿态 | ✅ 核心能力，可靠 |
| 骨骼连接关系 | 哪个点连哪个点，关节角度 | ✅ 核心能力，可靠 |
| 关键点可见性 | 某个点是否被遮挡 | ✅ 可靠 |
| 粗略比例检查 | 肩宽和身高的大致像素比 | ⚠️ 受透视/焦距/姿态影响，粗可用 |
| 精确体型测量 | "腰围 78cm" | ❌ 做不到 |
| 身体几何形态 | hourglass/pear 等身型 | ❌ 做不到 |
| 三维人体重建 | 3D mesh | ❌ 做不到（需要 SMPL/HMR 等额外模型） |

### OpenPose 在我方案中的实际角色

回顾我的流程设计文档，OpenPose 出现在两个位置：

**位置 1：体型偏差检测**

我的原始方案："用 MediaPipe/OpenPose 提取关键点 → 计算肩宽/身高比、腰宽/身高比 → 与用户参数推算的区间比对"。

ChatGPT 的批评是对的：这些像素比例受透视/焦距/姿态/衣物遮挡影响，不够可靠。我已经在争议 3 中修正为"V1 纯数据收集，不做自动判定"。

**位置 2：姿态控制（生成时的条件输入）**

这个用例是正确的——OpenPose skeleton 作为生成模型的姿态条件输入，告诉模型"画一个站立的人"。但 V1 不做姿态控制（V1 用真实照片直接做 VTON，不需要 OpenPose 条件），所以这个用例在 V1 也不触发。

### 修正后的 OpenPose 定位

```
V1：
  OpenPose / MediaPipe 的唯一用途：
  → 照片质量检测（关键点是否可见、姿态是否正面）
  → 不用于体型判定
  → 不用于姿态控制
  → 不用于精确比例计算

V2（待 POC 验证后）：
  → 姿态条件生成（如需生成非标准姿态的试穿图）
  → 粗粒度比例监控（基于 V1 收集的数据确定可靠性）

V3：
  → 配合 SMPL/SMPL-X 做三维人体重建
  → 精确体型控制
```

**判定：ChatGPT 胜。OpenPose ≠ 体型模型。V1 中 OpenPose 仅用于照片质量检测，不用于体型控制。体型信息来自真实照片 > 完整测量值 > BMI 粗分类。**

## 争议 6：现在是否可以直接锁定具体 VTON 模型？

### ChatGPT 的立场

在没有真实 POC 前，"VTON"可以成为架构方向，但不能锁死某一个具体模型为最终生产模型。必须验证你列的 19 项。"开源模型可以运行"不等于"可以合法、稳定地作为商业产品使用"。V1 架构应为"VTON 抽象接口"，通过 POC 决定实际 Provider。

### 我的回答：**完全同意。不锁模型，走抽象接口 + POC。**

你列的 19 项验证点每一项都是合理的。我的原方案里提到"Kolors VTON API"等具体模型，这些应该作为 POC 的候选目标，不是 V1 的锁定选择。

特别关键的几点：

**"开源模型可以运行" ≠ "可以合法、稳定地作为商业产品使用"**

这是最重要的区分。IDM-VTON 在 GitHub 上有代码，但它用的是 Stable Diffusion 的底层，商用需要 Stability AI 的商业授权。CatVTON 类似。Kolors VTON 的商用授权也需要确认。这些都需要在 POC 阶段搞清楚。

**微信云开发的特殊约束**

- 云函数没有 GPU → 自部署不可行（除非另租 GPU 服务器）
- 云函数超时 20s → VTON 推理时间必须 < 15s（留 5s 给业务逻辑）
- 需要异步模式 → VTON API 必须支持回调或轮询
- 数据隐私 → 用户照片发给第三方 API，需要确认隐私合规

### 修正方案

```
V1 VTON 架构：抽象接口 + 适配器 + POC 决策

1. 定义 VTON 抽象接口：
   - tryOn(personImage, garmentImage, category) → tryOnResult
   - category: 'upper' | 'lower' | (future: 'shoes', 'dress')
   - 返回：试穿图片 URL + 质量元数据
   - 异步模式：submit → taskId, poll(taskId) → result

2. 实现适配器模式（与当前 AIProvider 一致）：
   - VTONProvider 接口
   - KolorsVTONAdapter implements VTONProvider
   - FutureAdapter implements VTONProvider
   - 切换 Provider 只改适配器，业务逻辑不变

3. POC 阶段验证（见 E 部分）

4. V1 不在代码中写死任何具体模型名
   - 配置化：Provider 选择通过环境变量/配置文件
   - 可切换：运行时切换 Provider 不需要改代码
```

**判定：ChatGPT 胜。V1 使用 VTON 抽象接口，不锁定具体模型，通过 POC 决定 Provider。**

**六条全输。每一条 ChatGPT 的反对都打到了我方案的结构性缺陷。**

## D：最终确定的 V1 架构

V1 核心流程（第四次修订，经完整辩论后）
═══════════════════════════════════════════════

[阶段一：人物输入] — 0~2 次 API 调用

    ↓
  ├── 合格 → 直接作为 VTON 人物输入

  │
  └── 不合格 + 用户无法提供合格照片

      → 明确标注"AI 估算形象"
      → 最多 2 次 AI 调用（1 高清正面 + 1 合成三视图预览）
      → 后台记录关键点比例数据（纯日志，不做判定）

  用户上传服装原图 + 选择品类（上装/下装）
    → 直接作为 VTON 服装输入
    → 不生成四视图
    → 不做额外处理

[阶段三：试穿合成] — 1~2 次 VTON API 调用

  人物图（真实照片 / AI 锚定图）+ 服装原图

    → 模式 A：1 件上装 → 1 次 VTON
    → 模式 B：1 件下装 → 1 次 VTON
    → 模式 C：1 上 + 1 下 → 2 次 VTON（分区替换）
    → 画面完整性硬检测（人脸在/肢体全）
    → 存入 tryon_results

[阶段四：结果展示] — 0 次 API 调用

  1 张正面试穿图
    → 全屏查看/保存/分享/收藏
    → AI 生成标识
    → 默认白底，隐藏"简约室内"实验开关做 A/B 测试

═══════════════════════════════════════════════

═══════════════════════════════════════════════

  ✅ 参数翻译引擎（数值 → 视觉描述词）
  ✅ Negative prompt（所有 AI 生成步骤）

  ✅ 画面完整性硬检测
  ✅ 默认白底 + 隐藏场景实验开关
  ✅ 后台体型数据收集（纯日志）

═══════════════════════════════════════════════

  ❌ 配饰试穿

  ❌ 15% 体型偏差硬阈值
  ❌ 任何形式的自动体型判定

## E：必须做 POC 验证的事项

### POC-01：真实照片 vs AI 锚定图作为 VTON 输入

```
目标：确定 VTON 的人物输入应该用什么

方法：
  1. 准备 10 组测试数据（用户同意使用的真实照片 + 同一用户的参数）
  2. 对每组数据：
     Path A: 真实照片 → VTON → 试穿结果
     Path B: 参数 → AI 锚定图 → VTON → 试穿结果
  3. 比较指标：
     - 身份一致性（ArcFace 人脸相似度）
     - 体型保真度（人工评分 1-5）
     - 衣服保真度（人工评分 1-5）
     - 手部质量（人工评分 1-5）
     - 衣服边缘质量（人工评分 1-5）
     - 失败率（明显错误占比）
     - 推理时间
     - API 成本

判定标准：
  - 如果 Path A 在身份一致性上显著优于 Path B → 确认"合格照片优先"
  - 如果 Path B 在某些维度优于 Path A → 需要重新评估
  - 无论结果，都为 V2 的混合策略提供数据
```

### POC-02：VTON 模型/Provider 对比

```
目标：确定 V1 使用的 VTON Provider

候选：
  - Kolors Virtual Try-On API
  - 字节豆包 VTON API（如有）
  - 快手 Kling VTON API（如有）
  - 其他商业 VTON SaaS
  - 自部署 IDM-VTON（如租 GPU 服务器可行）

验证项（ChatGPT 列的 19 项）：
  1. 人物输入格式要求
  2. 衣物输入格式要求
  3. 输出分辨率
  4. 全身支持（半身还是全身）
  5. 多衣物支持（1件/2件/更多）
  6. 长款服装支持（风衣/长裙）
  7. 裙装支持
  8. 外套支持
  9. 鞋子支持
  10. 配饰支持
  11. API 可用性（SLA/并发/地域）
  12. 推理时间
  13. GPU/调用成本
  14. 并发能力
  15. 失败率
  16. 商用授权
  17. 商业 API 稳定性
  18. 数据隐私（照片是否留存在第三方）
  19. 微信云函数接入难度

每个 Provider 用相同 20 张测试图（10 人物 + 10 服装）评测
```

### POC-03：上装+下装分区 VTON

```
目标：验证 2 次 VTON 级联的可行性和质量

方法：
  1. 准备 10 组"上装+下装"组合
  2. 对每组：
     Step 1: 人物图 + 上装 → VTON(upper) → 中间图
     Step 2: 中间图 + 下装 → VTON(lower) → 最终图
  3. 逐项检查：
     - Step 2 是否完美保留了 Step 1 的上装？
     - 上装和下装的衔接处是否自然？
     - 两步之间的体型是否一致？
     - 整体质量 vs 单件试穿是否下降？

判定标准：
  - 如果 90%+ 的案例 Step 2 完美保留 Step 1 → 模式 C 可上线
  - 如果 < 70% → V1 只做模式 A/B（单件）
  - 70%-90% 之间 → V1 上线但标注"二件套效果可能不如单件"
```

### POC-04：背景对 VTON 质量的影响

```
目标：确定 V1 默认背景策略

方法：
  1. 准备 5 组测试数据
  2. 每组用 3 种人物输入背景：
     - 白底
     - 简约室内（浅灰墙面 + 木地板 + 自然窗光）
     - 复杂背景（真实场景）
  3. 相同服装，比较 VTON 输出质量：
     - 伪影率（多出手指/面部变形等）
     - 衣服边缘质量
     - 人物与背景的分离质量
     - 身份保持度

判定标准：
  - 白底显著优于其他 → V1 默认白底（当前方案）
  - 简约室内 ≈ 白底 → 可以给用户选择
  - 复杂背景也可行 → V2 可开放场景选项
```

### POC-05：BMI 粗分类在 prompt 中的效果

```
目标：验证 BMI → 描述词 → 生成图 的链条精度

方法：
  1. 准备 5 个 BMI 档位的参数（偏瘦/正常/偏重/肥胖/极度肥胖）
  2. 每档用 BMI 推导的 prompt 生成 5 张锚定图
  3. 人工判断生成图的体型是否符合预期的 BMI 档位
  4. 对比：BMI 粗分类 vs 完整测量值分类的准确率差异

判定标准：
  - BMI 粗分类准确率 > 80% → 可作为"仅身高+体重"场景的降级方案
  - BMI 粗分类准确率 < 60% → BMI 在 prompt 中也不可靠，需要其他方案
```

### POC-06：关键点比例与体型判断的相关性

```
目标：为 V2 的自动体型判定提供数据基础

方法：
  1. 收集 100+ 张 AI 锚定图的关键点数据
  2. 每张图人工标注体型是否合理（1-5 分）
  3. 计算各比例指标与人工标注的相关性：
     - 肩宽/身高
     - 腰宽/身高
     - 腰宽/肩宽
     - 腿长/身高
  4. 确定：哪些指标有判别力？哪些没有？

判定标准：
  - 如有指标相关性 > 0.7 → V2 可基于该指标做自动判定
  - 所有指标相关性 < 0.5 → V2 也不做自动判定，继续数据收集
```

### POC-07：白底 vs 简约室内的用户感知

```
目标：验证"白底 = 假"的假设是否成立

方法：
  1. 准备 10 组试穿图（同人物同服装，白底 vs 简约室内各 1 张）
  2. 用户测试（20 人）：
     - "哪张更真实？"
     - "你更信任哪张的效果？"
     - "你愿意基于哪张图做购买决策？"
  3. 统计偏好比例

判定标准：
  - 简约室内偏好 > 60% → V1.5 上线场景选项
  - 白底偏好 > 60% → V1 保持白底
  - 无显著差异 → V1 白底，不折腾
```

## F：明确删除的错误设计

| # | 删除项 | 原来在哪个方案中 | 删除理由 |
|---|--------|----------------|---------|
| F1 | 强制所有用户 AI 生成人物锚定图 | 原始流程设计 | AI 重建是有损变换，真实照片是更好的 VTON 输入 |
| F2 | 15% 体型偏差硬阈值 | 优化方案 | 无数据支撑，不应作为产品硬规则 |
| F3 | BMI 作为主要人体几何约束 | 优化方案 | BMI 不能推导身体几何形态，真实测量值优先 |
| F4 | OpenPose 用于体型精度控制 | 流程设计 | OpenPose 是姿态模型，不是体型模型 |
| F5 | 锁定 Kolors VTON 为 V1 模型 | 优化方案 | 无 POC 不锁模型，开源能跑 ≠ 商用合法 |
| F6 | 服装四视图生成 | 原始流程设计 | VTON 不需要，V1 不做视频，无使用场景 |
| F7 | 视频生成 | 原始流程设计 | 3s 微动态与静态图差异太小，图生视频质量不可控 |
| F8 | 多角度试穿图 | 辩论修正方案 | 3 次 VTON 太贵，V1 只做正面 1 张 |
| F9 | 3 件及以上衣物试穿 | 优化方案 | VTON 级联 >2 件误差不可控 |
| F10 | 叠穿支持 | 优化方案 | 标准 VTON 无法做"在 T 恤外面加外套" |

## 比分总结

| 争议 | 结果 |
|------|------|
| 1: AI 锚定图 vs 真实照片 | ChatGPT 胜 |
| 2: VTON 多件衣物 | ChatGPT 胜 |
| 3: 15% 体型阈值 | ChatGPT 胜 |
| 4: BMI 作为体型约束 | ChatGPT 胜（我补充了 BMI 作为最低可用信号的边界场景） |
| 5: OpenPose ≠ 体型模型 | ChatGPT 胜 |
| 6: 锁定 VTON 模型 | ChatGPT 胜 |

**0:6。六战全败。**

这不是客套。六个争议点每个都指出了我方案中的结构性错误：
1. 用 AI 重建替代真实照片——对 VTON 核心能力的误解
2. 对多件衣物的处理过于乐观——没有直面 VTON 的单件限制
3. 无数据设阈值——工程上的不严谨
4. BMI 当主约束——对体型维度信息的过度压缩
5. OpenPose 混同体型模型——概念混淆
6. 无 POC 锁模型——对商业落地的风险低估

方案已经做了四次修订。每修订一次，V1 的范围就更小、更聚焦、更诚实。这不是退缩——这是把不能兑现的承诺删掉，只留真正能做的。
